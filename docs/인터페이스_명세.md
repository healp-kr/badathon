# 인터페이스 명세

**2026-08-13 · api_version 1.1.0 · 로그 schema_version 1.0.0**
*1.1.0 변경 — 강도 상한이 종목을 지우지 않게 됐다(§3-1). 출력에 `처방.강도컷`·`강도주의` 추가.*

앱과 GIS 레이어는 이 문서만 알면 된다. 내부 구조(`assignment/`, `recommendation/`)는
몰라도 되고, 직접 임포트하지 말 것.

```python
from serve import serve
result = serve(payload, top_n=10)      # 날씨 재정렬을 쓸 거면 넉넉히 받는다
```

**`top_n` 을 기본값(3)으로 두면 날씨 재정렬이 동작하지 않는다.** 야외형 사용자는 상위 3개가
전부 실외라, 끌어올릴 실내 종목이 애초에 목록에 없다. `serve(payload, top_n=10)` 으로 후보를
받고 `api.context.apply_context(..., display_n=3)` 이 재정렬 **뒤에** 자르는 것이 정해진 순서다.

학습이 없다. 파라미터 파일을 읽어 계산만 하므로 모델 서버가 필요 없다.
같은 입력은 항상 같은 결과를 낸다(`request_id`·`생성시각`만 다름).

## 1. 입력

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `나이` | int | **필수** | 만 나이. 경계 동작은 §3 참조 |
| `성별` | `"남"` / `"여"` | **필수** | |
| `키` / `몸무게` | number | 권장 | 체력 신체조성 축 추정에 쓰인다. 없으면 그 축은 또래 평균으로 처리 |
| `규칙적참여` | bool | 권장 | 설문 Q0. `false`면 선호 유형을 배정하지 않는다 (기본값 `true`) |
| `운동빈도` `운동요일` `운동시간대` `운동목적` `운동강도` `체력인지` | str | 권장 | 선호 유형 배정용 6문항. **선택지 문자열이 모델 범주와 정확히 일치해야 한다** |
| `자주해온운동` | list[str] | 권장 | 설문 Q12 |
| `관심운동` | list[str] | 권장 | 설문 Q11 |
| `체력자가평가` | dict[str, 1~5] | 권장 | 축별 5단계. 성인은 `근력·근지구력·순발력·유연성`, 노인은 `근력·하지근기능·협응력평형·유연성` |
| `불편부위` | list[str] | 선택 | `무릎·허리·어깨·발목·손목`. 해당 부담 종목을 추천에서 뺀다 |
| `지역` | str | 선택 | 현재 모델 입력이 아니다. 시설 검색은 GIS 레이어에서 별도 처리 |

**문항 선택지 문자열은 `설문문항_v1.md` 가 정본이다.** 한 글자만 달라도 그 문항은
조용히 무시되고(주변화) 배정 정확도만 떨어진다 — 에러가 나지 않으니 더 위험하다.
매핑 표를 코드에 하드코딩하지 말고 양쪽이 같은 파일을 참조할 것.

응답이 없는 문항은 건너뛴다. 6문항 중 3문항만 있어도 동작한다(확률만 낮아짐).

### 종목 한 칸의 구조

```jsonc
{ "종목": "수영+아쿠아로빅, 수중발레+수구", "점수": 114.0,
  "선호점수비율": 6.2, "Lift": 1.98, "강도": "중",
  "부담부위": ["어깨"], "고령적합": "적합",
  "이유": "같은 유형에서 유독 많이 하는 종목 (평균 대비 2.0배)",
  "맞춤이유": ["원하시는 강도(중)와 맞음", "저녁에 하기 좋은 실내 종목"],
  "강도주의": "권장하는 강도('중')보다 강한 편입니다. 낮은 강도로 짧게 시작해 보세요",
  "주의": "강도 미확인 종목",
  "시설": { ... } }
```

`강도주의`와 `주의`는 **해당하는 종목에만 붙는 선택 필드**다.

- `강도주의` — 권장 상한을 넘지만 제외하지는 않은 종목. **목록의 뒤쪽으로 밀려 있다.**
  화면에 배지로 반드시 노출할 것. 이게 없으면 상한이 아무 의미가 없어진다
- `주의` — MET이 확인되지 않은 종목(11종). 내부적으로는 '중'으로 간주해 상한과 비교한다

`점수`는 **같은 응답 안에서만 비교 가능한 상대값**이다. 사용자에게 숫자로 노출하지 말 것.

## 3. 라우팅 — 경계가 셋 다르다

| | 선호 모델 | 체력 문항·모델 | 표시 라벨 |
|---|---|---|---|
| 노인 경계 | **60세** | **65세** | **60세** |

- 60–64세 → 선호는 노인, 체력은 성인 모델, 화면에는 노인. **의도된 설계다.**
- 19세 미만 → 체력 유형 없음(`체력유형: null`), 선호만
- `규칙적참여: false` → 선호 유형 없음. 관심 종목 기반으로 `익숙한운동`만 채워진다

### 3-1. 강도 상한은 원칙적으로 종목을 지우지 않는다 *(2026-08-13 변경)*

| | 동작 | 발생 조건 |
|---|---|---|
| **소프트** (기본) | 상한 초과 종목을 **뒤로 밀고 `강도주의` 배지**를 붙인다 | 그 외 전부 |
| **하드** | 상한 초과 종목을 `제외종목`으로 뺀다 | **노인(65+) + 전반적 저조형 + 배정 확정** |

- 부위(불편 부위)·연령(고령 비권장) 컷은 **종전대로 하드**다. 바뀐 것은 강도뿐이다.
- **배정이 모호하다는 이유로 상한을 낮추지 않는다.** 확신도가 낮은 것은 "체력이 낮다"가 아니라
  "우리가 모른다"이므로, 종목을 지우는 근거가 되지 못한다. 대신 `안내`에 문구가 실린다.
- 근거: 지침 원문이 저조형에 대해 *"가볍거나 중간 강도로 주 1회부터 시작해 점차 높인다"* 이지
  고강도 금지가 아니다. 자세한 경위와 수치는 `강도라벨_재검토.md`.

## 4. 시설 검색 조건 (GIS 인계)

이 API는 **주변 시설을 찾지 않는다.** "무엇을 찾아야 하는가"까지만 알려준다.

```jsonc
{ "종목": "수영+아쿠아로빅, 수중발레+수구", "갈래": "새로운운동",
  "시설유형": ["[공공체육시설] 수영장", "[민간체육시설] 수영장"],
  "시설대분류": ["공공체육시설", "민간체육시설"],
  "시설불필요_비율": 3.2, "신뢰도": "보통" }
```

- `시설유형` — 검색 키워드. 국민생활체육조사 세부시설 69종 분류. 실제 이용 분포에서 산출
- `신뢰도: "낮음"` — 세부시설 응답률이 낮은 종목(**축구·농구·체조·줄넘기·족구**).
  학교·직장 시설 이용이 많아 잡히지 않는다. 검색 결과가 없어도 이상하지 않다
- `시설불필요_비율` — 집에서 하는 비율. 높으면 장소 연결의 가치가 낮다
- `신뢰도: "없음"` — 표본 부족으로 시설 분포를 내지 않은 종목

## 5. 오류

계약 위반은 `serve.RequestError`(ValueError 하위)로 던진다 — 4xx 로 응답할 성질이다.
필수 누락, 성별·나이 범위, 키·몸무게 음수, 자가평가 1~5 벗어남, 타입 불일치.

**정상 처리이지만 결과가 비는 경우**는 오류가 아니다. `선호유형`/`체력유형`이 `null`이고
`라우팅.skip_reason`에 이유가 담긴다.

## 6. 로그 (필수)

```python
from logging_schema import events_for_request, interaction_event, self_measure_event

for event in events_for_request(payload, result, session_id, user_id):
    sink.write(event)
```

**v1부터 남겨야 한다. 소급 수집이 안 된다.** 이게 없으면 두 가지를 영원히 모른다 —
체력 자가평가 신뢰도(현재 정확도 50% 내외 추정)와, 근거 없이 정한 가중치들이 맞는지.

공통 필드: `event_id · event_type · occurred_at · schema_version · session_id · user_id ·
request_id · model_version`

| 이벤트 | 시점 | 왜 필요한가 |
|---|---|---|
| `onboarding_submitted` | serve 호출 | 응답 원본. 문항이 바뀌어도 재분석이 된다 |
| `assignment_made` | serve 호출 | 확률·확신도까지. 하드 라벨만 남기면 경계 사례 분석이 불가능 |
| `recommendation_served` | serve 호출 | 순위·점수·이유·제외 사유 |
| `sport_impression` | 카드 노출 | 클릭률의 분모 |
| `sport_click` | 카드 클릭 | |
| `facility_click` | 시설 클릭 | GIS 연결 지점의 전환율 |
| `sport_started` / `sport_completed` | 사용자 표시 | 실제 실행 여부 |
| `sport_dismissed` | 치우기 | **음성 신호. 없으면 클릭률만으로 편향된다** |
| `self_measure_submitted` | 검증 루프 | 자가평가와 짝지어야 r 추정 가능 |
| `feedback_submitted` | 피드백 | 난이도·만족도 |

`request_id`로 추천과 상호작용을 조인하고, `model_version`으로 어느 모델이 낸 결과인지
되짚는다. **파라미터를 바꾸면 `model_version`이 자동으로 바뀐다** — 비교 분석의 기준선이 된다.

### 검증 루프

```python
self_measure_event(session_id, request_id, model_version,
                   measures={"의자에앉았다일어서기": 14, "앉아윗몸앞으로굽히기": 8.5},
                   self_rating={"하지근기능": 3, "유연성": 2})
```

측정값만 받고 자가평가를 함께 남기지 않으면 아무 소용이 없다. **반드시 짝으로.**

## 8. 알려진 한계 — 화면 문구에 반영할 것

- **체력 유형 정확도 50% 내외.** 자가평가 신뢰도에 좌우되며 현재 데이터로 측정 불가.
  단정적 표현("당신은 저조형입니다")을 쓰지 말 것. `ambiguous: true`면 `alternative`를 함께 노출
- **추천 근거는 인과가 아니다.** "비슷한 분들이 많이 하십니다"는 그들이 이미 하는 것이지
  그들에게 좋은 것이 아니다. "추천"보다 "비슷한 분들의 선택"이 정확한 표현
- **선호 유형은 확률이다.** 하드 라벨만 쓰지 말고 2순위(`runner_up`)를 함께 활용할 것
- **종목 강도 라벨이 전반적으로 높은 쪽으로 잡혀 있다.** Compendium 대표값을 "열심히 하는 버전"
  으로 고른 결과다(등산=배낭 종주 7.8, 농구=경기 7.5 등). 지금은 종목을 지우지 않으므로 피해는
  없지만, **화면에서 "세게 하면 고강도"라는 뉘앙스로 표기**할 것. 재검토표는 `강도라벨_재검토.md`
- 근거가 없는 항목: 순발력 보완 운동(v1 제외), 종목별 부담부위 태깅, 11개 종목의 MET,
  점수 가중치 전반. 자세한 것은 `근거자료_운동처방.md` §6
